# Built-in sub-agents

Design notes moved out of AGENTS.md. Precedence/persistence rationale: `docs/adr/0003-built-in-subagent-toggle.md`.

- The global `builtInEnabled` switch is persisted in `~/.pi/agent/agents/settings.json` and defaults to `true` when the file or field is absent. An explicit `false` disables it. Malformed settings fail closed; atomic updates preserve unknown fields. Concurrent sub-agent prompts are queued per parent session (`maxConcurrent`, default 10).
- A per-project override (`projects: { [root]: boolean }` in the same file, keyed by sidebar project root so worktrees share it) wins over the global switch, which is only the default: same rule as resource overrides (a project may switch it on while the default is off). Setting a project back to the default drops its entry; the older off-only `disabledProjects` list reads as `false` entries and is rewritten on the next write. Start and resume both check the effective state against the parent cwd. With no enabled profile the factory registers no tools.
- The inline built-in extension factory is always present so reloading an existing wrapper can apply setting changes, but it registers no tools while disabled. After changing the switch, the user must explicitly reload the current session.
- When enabled, only a recognized legacy `pi-subagents` extension that registers any reserved tool (`Agent`, `get_subagent_result`, `steer_subagent`, or `abort_subagent`) is removed. Unrelated extensions remain loaded, and resolved conflict diagnostics are discarded.
- Runtime `Agent` dispatch checks the setting again so a stale tool call cannot start a subagent after the feature is switched off.
- See `docs/adr/0003-built-in-subagent-toggle.md` for the precedence and persistence rationale.
- Agent profile files (`~/.pi/agent/agents/*.md`, project `.pi/agents/*.md`) may be shared with other runtimes. A save round-trips frontmatter keys this app does not own (`name`, `allowed_subagents`, `exclude_extensions`, `disallowed_tools`, `prompt_mode`, `isolation`, …) and carries `ext:` tool selectors through `tools:`.
- Managed keys are exactly `description`, `display_name`, `tools`, `load_skills`, `load_extensions`, `enabled`, `inherit_context`, `run_in_background`, `model`, `thinking`, `max_turns`. The `skills` / `extensions` aliases are seeded on first save and kept in step while they are booleans; a hand-authored whitelist such as `extensions: pi-advisor-flow` is never rewritten. The two flags fall back to those aliases when `load_skills` / `load_extensions` are absent.
- Profile precedence matches pi-subagents: project `.pi/agents` > workspace `.agents/agents` > global > built-in, and the top file wins whole — a disabled top file never falls back. The Agents list is the user's global configuration and shows one row per name without exposing storage layers: built-ins are edited directly and saved as a global copy (tagged "modified", with Restore default = delete that copy); Save stays disabled until a field changes so opening one never forks it. The row switch (`setSubagentProfileEnabled`) toggles the effective file: an untouched built-in gets a global `---\nenabled: false\n---` stub (it keeps following Pi Web updates), enabling a stub deletes it. Project/workspace files are honored and tagged "project file" (their switch edits that file). Availability per project is the Project page's switch; creating a project-scoped definition is only done through the create form's save location or import (below). New agents default to global.
- Two entry points, one editor. `components/AgentEditor.tsx` holds the state machine and detail form; the Agents page (both scopes, save-location selector) and the Project page (`fixedScope: "project"`) mount it, and both write the same files, so they stay in sync through the usual version-bump remount (`onChanged`). On the Project page an inherited definition is read-only until 「为本项目定制」 (`beginCustomize`, nothing is written until Save), the switch is availability here (`projectEnabled`), New/Import write project files only, and delete only applies to project files.
- Per-project agent model. In one project an agent is in exactly one state: follows global (no project file); disabled here (project stub); customized here (project file with the same name as a global/built-in one — it wins whole, no merging); project-only (project file, nothing to inherit). "Differs from global" means the stub and customized states, in every surface: the Project page's count, its per-row 「改用全局版本」 button, and 「全部恢复」 (which asks before deleting customized definitions; project-only agents stay because there is nothing to follow). Deleting a project file finds it by parsed name, not `${name}.md`. Customizing is done in the Agents page: the save-location selector (create form, and edit of an inherited agent) writes `<cwd>/.pi/agents/`; `saveSubagentProfile` seeds that new file's unmodeled frontmatter from the definition it replaces (`frontmatterSeedPath`), then the file stands on its own. A customized agent's page shows 「改用全局版本」 at the top. The Agents form edits global configuration, so a project stub does not make it read-only: it edits the definition below the stub (`editOwner`) and the selector is hidden until the stub is lifted.
- 「导入」 (AgentsImportDialog, save location defaults to global) byte-copies definitions from another project — never through the profile form, so unmodeled frontmatter keys survive. Sources are only the other checkouts known from session history (session `cwd`/`projectRoot`) whose `.pi/agents/` holds `.md` files (`listImportSources`); there is no free folder picker, and the route refuses any `sourceDir` that is not in that list (nothing is added to the file allow-list). The preview returns `existsIn` for both targets, so switching the target re-marks conflicts without refetching. An existing file name or logical agent name is skipped, never overwritten. Project agent files are per checkout and are not synced across worktrees (unlike resource overrides); tracked in git they arrive with the branch, otherwise importing from the main checkout into a worktree is the manual path.
- ProjectConfig hosts a Sub-agents group (one row per agent name) where the single switch means "available in this project" (`PATCH projectEnabled` → `setSubagentProjectAvailability`): a global agent is disabled here by a project disable stub, a project definition is toggled in place, and flipping back to the inherited state deletes the project file again. Stubs and customized agents count toward the differences total; 「重置为全局」 lifts the stubs and deletes the customized copies (after a confirm), and leaves project-only agents.
- Every write into `.pi/agents` or `.agents/agents` (PUT/DELETE with non-global scope, PATCH on a project/workspace-effective file, projectEnabled, project-scope import) goes through `assertProjectScopeTrusted`, the same project-trust gate as resource overrides; a repo whose only project resource is `.pi/agents` is not trust-requiring (the SDK's list excludes `agents`), so ordinary projects are unaffected.
- `Agent`, `get_subagent_result`, `steer_subagent`, and `abort_subagent` use SDK `exposure: "model-only"`: they remain declared/active for model calls but are never available through `ctx.executeTool()` or codemode scripts. Nested tool-call IDs are not transcript entries and cannot anchor a child session.
- `ext:` selectors in `tools:` are honored at spawn: they load only matching extension tools instead of every loaded extension tool. Names may be a file (with or without its extension), parent directory, npm package name (scoped or unscoped; source version pins are removed). Extension names are case-insensitive and tool names exact; `ext:name`, `ext:name/`, and `ext:name/*` select the whole unit. Only `ext:*` is a global wildcard. Resolution uses the longest matching name and refuses ambiguous sources; files of one package share a unit, while top-level `local`/`auto` sources do not. `disallowed_tools` uses the same resolution, so a deny alias covers grants under another alias, including all-extension grants.
- Tool admission: a child that loads extensions with no `ext:` selector and no deny rule gets no `tools` allowlist, because the SDK fixes one at creation and would never admit a tool an extension registers at `session_start` or later (#883). `subagentToolOptions()` (`lib/subagents.ts`) then passes `noTools: "builtin"` with the profile's built-ins as `+name` entries, excludes the other built-ins, and excludes the reserved names (`Agent`, `get_subagent_result`, `steer_subagent`, `abort_subagent`, `generate_image`), so no extension can switch on a built-in the profile leaves out. A snapshot without `allExtensionTools` keeps its allowlist. `ext:` selectors and deny rules keep the spawn-time name allowlist, so a late tool from a selected extension stays out (known ceiling: the SDK admits by name only). `lib/subagent-late-tools.integration.test.mjs` pins spawn, reload, reopen, `ext:` and deny.
- `Agent` takes no `max_turns` or `inherit_context`: the profile's frontmatter alone sets the turn limit and parent-context inheritance (`thinking` falls back to the parent's level), so a guessed value cannot replace what the user configured. The agent-type list states each profile's `Parent context: none|chat text`, so the parent knows whether to paste material into `prompt`. A call that still sends either key validates (pi keeps undeclared keys) and the key is ignored, including on resume; transcripts from older versions render and resume unchanged.
- Turn limits apply to both start and resume. A continuing run gets at most one extra wrap-up turn; queued steer/follow-up messages and a handler's `continue` cannot bypass the budget. Wrap-up drains all existing steering together with the limit instruction. At exhaustion the queues are cleared and undelivered messages are reported with partial output; later steering is rejected until an explicit resume. Natural final answers, provider errors and cancellations keep their existing outcome semantics.
- A resumed background run's wave notification explicitly says it supersedes any earlier report from that child; first-run reports and tool-result details are unchanged. The report remains marked as host-delivered, not a new user instruction.
- Default subagent bash and PowerShell use `createProjectCommandBashOperations` on spawn and cold reopen, removing `PI_WEB_PASSWORD` and host runtime variables while preserving SDK session/model environment. User extension-owned shells keep their existing priority and remain user-controlled.
- Resources (settings, project overrides, skills, extensions, trust) always resolve from the parent's directory, the child session's header cwd. `isolation: worktree` only moves the tools into a tmpdir checkout, which has neither untracked `.pi/settings.json` nor a trust decision (`createAgentSessionServices` at the config cwd, then `{ ...services, cwd }`).
- Isolated runs auto-commit changes and preserve commits on a branch before removing the temporary checkout; a no-change run removes it without creating a branch. A checkout already missing when cleanup inspects it records an unknown change state, not “no changes”; the parent is advised to check repository branches for commits. Foreground results, background previews, and `get_subagent_result` include the recorded cleanup outcome (including after restart). Failed cleanup keeps the checkout and reports its path plus a safe, short reason, never raw git advice; inspect/merge decisions stay with the parent. Old results without a recorded outcome get no inferred note. The note precedes child output so preview truncation does not hide it.
- The chat's Agents popover keeps two rows per session: task above; non-default profile, effective model, lowercase thinking id and time in the existing 11px metadata line below. Live wrappers supply the current settings; disk-only children reuse the session context's active-branch settings (missing thinking = `off`). Full parsing is only for changed subagent scan rows; unchanged rows reuse their cached relation.
- Model choice: a profile's `model` is only a default; the `Agent` call's `model`/`thinking` override it. The agent may pick only from the session's `enabledModels` scope (every model with auth when unscoped); a profile's own `model` is user configuration and resolves against all configured models. Tool descriptions are fixed before the session's model scope exists, so a `before_agent_start` handler lists that same set in a `subagent_models` prompt section (capped at 40) while `Agent` is active. `parseSubagentModel` accepts `provider/id`, a unique bare id, and pi's `:level` suffix; it runs before the child session is created, and a miss lists the choices so the parent can retry instead of falling back. `resume` retains the child's model, thinking, tools, context, isolation and turn limit. It rejects `model`/`thinking`, non-empty `input_files`/`isolation` before dispatch; empty defaults (`[]`, `""`) remain compatible. Change the prompt, description or `run_in_background` to continue; start a new child to change creation options.
- `input_files` are inlined in the child's first message, so their total is capped at about a quarter of the child model's context window (bytes ≈ window tokens), never above 512 KiB; an unknown window keeps 512 KiB (`subagentInputByteLimit`).
- `abort_subagent` lets the delegating model stop a queued or running child (a background run ignores the parent's Stop). It checks ownership, waits up to 5 s for the run to settle, and consumes the settled result so the parent gets no second completion notice; an already-settled run is reported as such. The transcript stays readable and resumable.
- Foreground `Agent` waits and `get_subagent_result wait=true` share `timeout_ms` (milliseconds, maximum 1800000 / 30 minutes; default 30 minutes for `Agent`, 5 minutes for `get_subagent_result`). `Agent` applies it after dispatch to the child completion wait, on both start and resume; it is ignored for background calls. A foreground timeout returns the child's session/status without stopping it, detaches the parent's abort signal, and registers its unread result once with the existing background wave. Before that handoff, parent Stop still aborts foreground children (including queued ones); background children continue as before. A result wait budgets the entire lookup/poll loop, including its first lookup; timeout does not consume the result. There is no seconds-based `wait_timeout` parameter.
- Completion is a family boundary: push, chime, browser notice and background-unread wait for all background wave members (queued/starting/running), unread wave results and report delivery, then the parent's last reply. The wave's existing `pending`/`results` and in-flight delivery set are the source of truth; `/api/agent/running` adds `subagentsActiveSessionIds`, separate from main-agent running/Stop/archiving state. Delivery hands completion to the parent only on the real `agent_start`, including SDK-deferred follow-ups, not when `sendCustomMessage()` resolves. A session visible in either split pane remains read; subagent sessions stay silent. While the family is unsettled (and not paused by Stop) the parent wrapper is not idle-disposed, its open tabs keep their event stream for the final reply, and a report that found the parent busy compacting or running a shell command is delivered once that ends. Known gap: a report reply the SDK had already deferred before Stop still announces completion.
- Parent Stop does not stop background children: it pauses automatic follow-ups until the next accepted user prompt, preserving unread reports. Their later completion must not produce a surprise completion notice or unread marker; stopped parents stay notification-suppressed even across idle-wrapper replacement. A user prompt resumes normal wave delivery and completion.
- Delegation guidance is a `<delegation>` system-prompt section (`subagentDelegationSection()`, set in `before_agent_start` while `Agent` is active), not `promptGuidelines` in the shared `<rules>` list. The wording is deliberately moderate: single lookups stay with the parent, parallel edits need disjoint files or a worktree, unread background results arrive after the parent's current run settles and `get_subagent_result wait=true` is only a within-run join point. `explore`/`plan` get a rule only while enabled; other enabled profiles are listed by name.
- A new child with `load_skills` and a `read`/`bash` tool also gets its skill catalog as a hidden (`display: false`) custom message delivered with the task (`deliverAs: "nextTurn"`, `subagentSkillCatalogMessage()`): the `<skills>` system-prompt section alone is often skipped and the child guesses paths. Resume does not resend it; it stays in the child's history.
