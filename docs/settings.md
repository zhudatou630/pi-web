# Settings pages: MCP, plugins, skills, project overrides, usage

Design notes moved out of AGENTS.md.

## Built-in MCP, codemode, tool search
- SDK sessions get none of pi's built-in extensions, so `startRpcSession()` adds `mcp`, `codemode`, and `tool-search` to normal sessions as `{ builtin: true, replaceable: true }` entries. That keeps CLI semantics: `-builtin:<name>` in `extensions` disables one, and an installed extension that registers `/mcp` (pi-mcp-adapter) replaces it. `llama.cpp` is not exported by the SDK and is not loaded. Chat only and sub-agents load none of them (a sub-agent's `tools:` allow-list would hide MCP tools anyway).
- The MCP extension gets `openUrl: () => {}`: OAuth URLs are shown through `ui.notify` and the redirect URL is pasted back through `ui.input`, since the browser is not on the server.
- Stdio MCP servers are spawned with the project bash environment (`sanitizeProjectCommandEnvironment`: no `PORT`, `NODE_ENV`, `NEXT_*`, `PI_WEB_PASSWORD`) through a `createTransport` that rebuilds the SDK's stdio transport with `inheritEnv: false` (`lib/builtin-extensions.ts`). If the SDK's `runtime.js` cannot load, MCP connections fail instead of falling back to the leaking default.
- Writing project config into a fresh folder trusts it, and trust is inherited by every folder below. `assertAutoTrustable()` (`lib/project-trust.ts`) therefore refuses that write for the filesystem root, home and its ancestors, and folders that contain another session's project root.
- MCP tools with `codemode`/`deferred` exposure stay callable whatever the active set, so `lib/read-only-tool-guard.ts` blocks every MCP tool call while no write-capable built-in is active (read-only preset). `readOnlyHint` is not trusted: pi does not verify it.
- Settings > MCP: design and scope in `docs/adr/0004-mcp-management.md` (graft pi's MCP, never re-host it). `lib/mcp-config.ts` reads/writes `mcp.json` with our bounded reader and locked atomic writer under pi's rules (`lib/mcp-config-read.ts`, `lib/mcp-config-file.ts`); Test (`lib/mcp-check.ts`), sign-in/out (`lib/mcp-sign-in.ts`), and paste import (`lib/mcp-import.ts`) call SDK modules the package does not export (`McpServerConnection`, `signInMcpServer`, `runMcpCommand`, …), loaded by file path with `webpackIgnore`/`turbopackIgnore` (a computed import is otherwise rejected by Turbopack); `lib/pi-sdk-compatibility.test.mjs` lists them. After an SDK upgrade restart the dev server: a server started before `npm install` keeps the old modules and fails these imports with missing-export errors. The list follows pi's `loadMcpConfig` (validity, precedence, and errors are pi's; invalid entries are errors, not rows) and, like pi, skips an untrusted project's `mcp.json` (`project.ignored`). `/api/mcp` responses never carry env/header/client-secret values or URL queries (`lib/mcp-view.ts`); only `GET /api/mcp?scope=&name=` (Edit JSON) returns an entry as written. A project entry without `command`/`url`/`type` (pi 1.0.1+) only overrides `enabled`/`exposure`/`toolExposure` of the global server: the global row shows the effective values with `projectOverride`, its switches write to the override (`PATCH { override: true }`, pi's `updateMcpServerConfig(..., { override: true })`), and "Disable/Enable in this project" / "Use global setting" add or delete it. Per-tool `toolExposure` edits go to the same place; the first one in an override copies the global rules, since pi replaces the whole map. Project `mcp.json` writes are trust-gated like project agents and record trust for the project the user just authored; a project entry with `auth` is refused (pi skips it). Sign-in runs on the server like `pi mcp login` (`/api/mcp/sign-in` SSE): a local browser completes through the loopback callback, a remote one pastes the redirected address. Sessions waiting for that sign-in reconnect at their next turn; config changes still need the reload notice.
- The built-in extensions are `builtin:<name>` resources in `lib/project-resource-overrides.ts` (pi's config-selector rules: the path is its own pattern, no plain entry is added). Their global switches live on the MCP page, per-project ones on the Project page; the Plugins page hides them.
- Notices naming `/mcp` (startup "MCP servers need attention", `/mcp` status) get an "MCP settings" link (text match on pi's English copy, URLs excluded). URLs in notices render as "Open link (host)"; notices with a URL stay 60s, ones with 3+ lines 15s. Notices emitted while no view is attached (MCP's startup report before a new session's SSE connects) are replayed to the next view if under 2 minutes old. An expanded tool card lists the result's `nestedCalls` (the tools a codemode script called; pi records no results for them). MCP tools share one plug icon (`ToolIcon`), since server tool names defeat the name heuristics. `/mcp` argument completions are TUI-only; the composer shows its usage signature instead.
- `defaultTools` may be a `+name`/`-name` delta; read it through `SettingsManager.getDefaultTools()` or `resolveDefaultTools()` in `lib/powershell-settings.ts`, never as a plain list.

## Plugins and skills
- `/api/plugins` uses pi's `SettingsManager` + `DefaultPackageManager` for global/project package install, remove, update, enable, and disable. Disabling writes empty `extensions/skills/prompts/themes` arrays for that package entry.
- `/api/skills` lists every skill configured for the cwd, loaded or not: loaded ones come from `DefaultResourceLoader` (settings paths, package skills, project `.agents/skills`, extension-provided), switched-off ones are parsed from `resolveScopedResources()` paths (`lib/skills-service.ts`), so a skill turned off can be turned back on. Each carries `enabled` (effective here) and `globalEnabled` (null when it has no global switch).
- One switch meaning across settings pages: load or not. Skills/Plugins switches are global (`setGlobalResourceEnabled`, the `pi config` user-settings filter; Plugins has one per package resource of every kind), This project switches are per project. `PATCH /api/skills { enabled }` is that global switch. Model auto-invocation is a property of the skill file, set in the skill detail page only (This project shows a read-only "manual only" tag that links there): `{ disableModelInvocation }` edits only the `disable-model-invocation` frontmatter key on the target `SKILL.md`; keep that surgical so user formatting survives. `PATCH /api/skills` authorizes by cwd (same as GET) plus exact `filePath` membership in `loadSkillsWithInstallInfo(cwd)`, not by resolving the skill file into extra allowed roots. Package skills (`sourceInfo.origin === "package"`) are refused with 409 and their switch is disabled: the package owns that file (a git checkout would go dirty, an npm update would drop the edit).
- The skill detail page shows the `SKILL.md` body (frontmatter stripped) read through `GET /api/skills?cwd=&filePath=`: same cwd check, then exact `filePath` membership in the loaded list, 1 MB cap. Rendered with `markdown-file-preview` (prose face) at chat-scale headings.
- `/api/skills/install` shells through `npx skills add ... --agent pi`; project installs run with the selected cwd.
- Settings pages share one "reload to apply" banner (`components/ReloadNotice.tsx`). Agents, Images, Skills, Plugins, and Project each bump their own version in `SettingsPanel` on a change and are keyed by the others', so mounted pages refetch without losing the one being edited. The Project page also shows the sub-agent and image-generation project switches (same settings as the Agents and Images pages) and counts them among the differences that "Reset to global" restores. Turning a whole package off writes empty arrays and so drops its per-item global filters (pi has no separate package flag).
- Per-project overrides live in `lib/project-resource-overrides.ts`, a port of pi's `pi config --local` selector. The Settings > This project page (`components/ProjectConfig.tsx`, `GET/POST /api/project-overrides`) is the only editor: one switch per package/resource showing its effective state; flipping it to match the inherited (global) state drops the override, otherwise writes load/unload. Plugins/Skills lists only show a tag. Worktrees of one repo are one project to the user but pi reads only `<cwd>/.pi/settings.json`, so `lib/project-override-sync.ts` replays each change into every checkout (skipped when `.pi/settings.json` is git-tracked or cwd is a subdirectory) and into worktrees created by `/api/worktrees`. It replays overrides instead of copying the file: local package sources are relative to each checkout's `.pi`. Package resources become a project `{ source, autoload: false, <type>: ["+path"|"-path"] }` delta over the global install (a project entry without `autoload: false` replaces the package and clones a project copy); top-level resources become absolute-path patterns. Always write per-item patterns, never `!**`: the pi TUI reads only per-item entries. `/api/plugins` hides `autoload: false` project entries as packages and attributes their resources to the global package. Once the global package is gone, pi resolves such a delta as a project package and installs a copy into `<cwd>/.pi/npm|git`, so a global remove on the Plugins page drops the deltas over that package in every known project/worktree (`dropRemovedPackageDeltas()`). Only then: at any other time an `autoload: false` entry without a global base may be a deliberate project package (pi only filters what it loads). Project copies are never deleted (they may be shared), and a `pi remove` outside pi-web leaves its deltas behind. Several project entries with one identity: pi uses the last, so the override editor reads and writes that one. Writing the first override into a project that needed no trust records trust for it, since the user authored that file.

## Sidebar archive and multi-select
- Right-click a project (or use its ☰ button) → **Select sessions…** in either the normal list or Archived. This expands every session row in that project's current view, including pinned sessions in the normal view, without the six-row preview cap. The bottom action bar offers select all/none (including an indeterminate state), a selected/available count, Archive or Restore, Delete, and Cancel. Shift-click adds an inclusive range; Escape cancels. Running families and unpersisted sessions have disabled checkboxes and are excluded from select-all. When a row becomes ineligible or leaves the view, its stored pick and range anchor are removed; returning rows are not automatically reselected. The selection never spans projects or normal/archive views.
- Sidebar rows are main sessions and forks; a fork is an independent family, not part of its source's archive. Hidden subagents belong to their nearest main/fork root, even across working directories. Archive/restore maps selections to these family roots, needs no confirmation, and only changes sidebar state. Explicitly archiving a pinned session unpins it. **Archive old sessions (>7 days)** remains the protected smart filter; whole-project Delete sessions and Unarchive all shortcuts are removed in favor of explicit selection.
- Batch Delete uses `useConfirm()` (a modal native dialog with background interaction blocked), showing the exact count and that deletion cannot be undone. It deletes only the selected session files: surviving forks are reparented to the deleted session's parent (or become roots). Unlike the original single-session cascade, unselected subagents survive; a direct subagent of a deleted root becomes a standalone session by relabeling its relation metadata as `pi-web:detached-subagent`, preserving its provenance data, messages, and other entries. Single-session deletion retains its existing subagent cascade.
- `DELETE /api/sessions` accepts `{ ids: string[] }` (1–500 ids, each at most 256 characters matching `SESSION_ID_PATTERN`), with a 64 KiB wire-body limit enforced before JSON parsing, including chunked requests. It verifies real file and parent-directory paths against the real sessions root, regular JSONL files, and matching header ids (including cached paths and runtime fallbacks). One request-local header-only relation index is built per target directory and updated after successful mutations; transcript bodies are read for rewrites, plus existing usage accounting on deleted files. Before commit, file identities/timestamps/headers, rewritten bodies, and directory membership are rechecked. It reserves affected runtimes/files, refuses running/busy targets or children needing rewrites, and reuses the single-delete rollback/reparent/usage-accounting implementation. Requests return per-id `{ id, ok, status, error?, warning?, deletedSessionIds? }` results; one refusal does not roll back other successful ids. The UI closes tabs for successful ids, exits selection, refreshes, and displays failures. Sidebar cleanup is locked; a cleanup error after a committed delete is reported as a warning, not a false deletion failure.
- The unused whole-project `DELETE /api/projects` endpoint has been removed. Fork routes and RPC fork/clone commands refuse to copy a source reserved for deletion, including while its idle runtime is shutting down.
- Mutation reservations protect this server's runtimes, not another Pi process writing the same transcript. HEAD's single-delete implementation discovers children only in the target file's directory; this pre-existing behavior is retained for single and bulk deletion. **Cross-directory subagents can consequently survive with a missing parent and disappear from family-based lists**; this review does not extend deletion/reparenting across directories.

## Usage statistics
- `lib/usage-stats.ts` sums assistant `usage` per local day × hour × provider × model for every session file under `sessions/` (recursively: extensions nest subagent runs below a session directory), caching rows plus the header cwd in `~/.pi/agent/pi-web-usage-cache.json` keyed by `(size, mtimeMs)`. Cache entries outlive their files, and `commitSessionDeletes()` folds a file in before deleting it; every pi-web delete path (single, cascade, bulk) goes through it, so deleted sessions keep counting. v1 entries (no hour/cwd) stay visible until rescanned.
- Forks and context-inheriting subagents copy parent history; only messages at or after the file header's timestamp count.
- `GET /api/usage` starts an incremental scan, waits for its stat pass, then at most 1.5s more; a longer (cold/upgrade) scan returns the cached rows with `scan: { done, total }` and the page polls until it is null.
- Cost is repriced at current rates like tokscale: pi's `ModelRuntime` model cost (exact provider/model, then same id), then models.dev, then the recorded cost; otherwise the message is reported as unpriced. Flat rates, no long-context tiers. Model ids drop a router's `vendor/` prefix after pricing. The response is priced day × hour × model × project records; `lib/usage-view.ts` does all range/grouping/drill-down in the browser.
- Per-model tables add TTFT / TPS: the scan joins `pi-web:model-timing` calls to their assistant message by `message.timestamp` and keeps additive sums per row (avg = ΣTTFT / calls, TPS = Σoutput / Σdecode). Those tables keep one share column that follows the sort (as on phones) to make room. Cache entries scanned before timing lack `timed: true` and are rescanned; the cache version stays 2 because the installed service drops a newer-version cache, deleted sessions included.

- Model performance (session panel, "TTFT / TPS" row): pi stores no stream timing, so `lib/model-timing.ts` measures each assistant call live (start = `message.timestamp`, first non-empty text/thinking/tool-call delta, `message_end`; error/aborted calls skipped) and appends one `pi-web:model-timing` custom entry per `turn_end` (after the call's tool results, so branch copies keep it), before `agent_end` reaches the client so its stats reload sees it. Math follows DeepSeek Harness: avg TTFT = ΣTTFT / calls, tok/s = Σoutput / Σdecode. Calls whose decode is under `MIN_DECODE_MS` (300 ms) arrived in one burst (unstreamed tool args, hidden reasoning, buffering) and count toward TTFT only; the filter applies at fold time, so recorded data stays raw. The session reader attaches each call as `modelTiming` on its assistant message (whole-file lookup, so paged history keeps it); the reply footer applies the same math to that reply group's calls (desktop only). Only runs driven by pi-web have data; subagents are not recorded.

## Auth and model config
- `ModelsConfig` combines models from `~/.pi/agent/models.json` with provider auth status from pi's `AuthStorage`/`ModelRegistry`. After saving definitions, re-select the model in an open session to apply them. Selection refreshes only that provider offline; unchanged definitions are not rebound, and same-id updates keep the session's thinking level (clamped to the updated capabilities).
- User-config saves (`models.json`, sidebar state, subagent settings/global profiles, and image-generation settings) follow file symlinks and atomically replace the real target in its own directory; dangling links are refused. The writers retain their private `0600` mode and existing locking. Project-scoped agent writes do not opt into symlink following. SDK/PowerShell `settings.json` writes already preserve links in place; MCP has its own boundary-checked link resolution.
- Provider listing is capability-driven, never id-driven: `lib/provider-listing.ts` decides membership from `auth.apiKey.login` / `auth.oauth` plus the stored credential type, so dual-auth providers (anthropic and github-copilot today — which providers declare both changes between SDK releases, so never assume it from an id) appear exactly once and never fall through both lists (#309). `lib/provider-listing-runtime.ts` adapts `ModelRuntime` to those pure helpers.
- auth.json holds **one** credential per provider and `ModelRuntime.logout()` deletes whichever it is. The delete routes therefore use `removeStoredCredentialIfType()` to compare and delete under the same file lock used by pi's auth storage. `ModelsConfig` also refreshes *both* provider lists after any auth change — refreshing one leaves a dual-auth provider rendered twice.
- OAuth/device-code/manual-code flows are streamed by `GET /api/auth/login/[provider]`; manual code responses POST back with a short-lived token stored in `globalThis.__piLoginCallbacks`.
- API-key routes store and remove keys through `AuthStorage`. Status endpoints must never return the raw key.
- The model test route is `app/api/models-config/test/route.ts`; `app/api/models/test/` is not a real route.
- Custom model definitions can override Base URL in Advanced settings; blank inherits the provider URL. API and URL inherit independently; catalog overrides do not support either field. Fill uses the effective URL, and connection tests discard results from an older draft.
- Model advanced settings edit `samplingParams` ("Extra request parameters") as one JSON object per model, for `models[]` definitions and catalog `modelOverrides` alike; it applies in every cwd. The SDK merges it into the request body only for `openai-completions`, `openai-responses`, `azure-openai-responses` (effective `model.api || provider.api`). Blank deletes the key. Non-object text stays in the draft as a string, keeps the page dirty, and blocks save (client and `writeModelsConfig`) and the model test. Override edits keep keys the editor does not manage (`samplingParamsByThinkingLevel`, …) and saved override fields untouched by the edit (`diffModelOverride` `previous`). Limit: the catalog has already merged the saved override, so the editor strips the saved keys to approximate the base model; a base key with the same name is hidden (no shipped model has `samplingParams`).
